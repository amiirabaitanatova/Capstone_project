# Прогноз удовлетворённости клиента для маркетплейса Olist

Capstone-проект: предсказание низкой оценки клиента (по данным, известным на момент доставки заказа), чтобы бизнес мог вмешаться до того, как клиент оставит негативный отзыв публично.

## Бизнес-контекст

Olist — крупный бразильский маркетплейс, объединяющий тысячи небольших продавцов на одной платформе. После каждой доставки клиент оставляет оценку от 1 до 5 звёзд. Низкая оценка — репутационный риск для продавца, потерянный повторный клиент и сигнал о проблеме в логистике, который руководство узнаёт только постфактум.

**Бизнес-вопрос:** можно ли предсказать, что клиент поставит низкую оценку, ещё до того как он её оставил — основываясь только на данных, уже известных в момент доставки (тип товара, сумма, способ оплаты, продавец, сроки доставки)?

## Датасет

Официальный открытый датасет Olist с Kaggle: [brazilian-ecommerce](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce) — реальные анонимизированные коммерческие данные, 2016–2018 гг., свыше 96 000 доставленных заказов.

Исходные 9 CSV-таблиц объединены через SQL (JOIN + агрегация) в единую таблицу признаков на уровне заказа. Итоговый набор признаков после SQL-этапа:

| Признак | Описание |
|---|---|
| `approval_time_days` | время между покупкой и подтверждением оплаты, дней |
| `shipping_prep_days` | время между покупкой и передачей заказа перевозчику, дней |
| `carrier_to_customer_days` | время в пути от перевозчика до клиента, дней |
| `total_delivery_days` | общее время доставки (покупка → вручение клиенту), дней |
| `delivery_delay_days` | факт минус обещанный срок доставки (положительное = опоздание) |
| `n_items` | количество товарных позиций в заказе |
| `n_distinct_products` / `n_distinct_sellers` | количество уникальных товаров / продавцов в заказе |
| `total_price` / `avg_item_price` | суммарная / средняя цена товаров в заказе |
| `total_freight_value` | суммарная стоимость доставки |
| `n_payment_types` | сколько разных способов оплаты использовано |
| `max_installments` | максимальное число рассрочек по заказу |
| `total_payment_value` | итоговая сумма оплаты |
| `product_category` | категория товара (переведена на английский) |
| `product_weight_g` / `product_photos_qty` | вес товара / число фото в карточке |
| `customer_state` / `seller_state` | регион клиента / продавца |
| `same_state` | флаг: клиент и продавец в одном штате |
| `review_score` | оценка клиента 1–5 (целевая переменная) |

## Как воспроизвести

1. Загрузить 9 CSV-файлов датасета в SQLite.
2. Выполнить `SQLite.sql` — на выходе таблица `model_features`.
3. Экспортировать `model_features` в CSV и открыть `capstone.ipynb`.
4. Выполнить ноутбук целиком сверху вниз.

## Этапы работы

### 1. База данных и SQL
9 таблиц датасета загружены в SQLite. Признаки уровня заказа (сроки доставки, агрегаты по товарам и оплате, категория товара) собраны SQL-запросами с `JOIN` и `GROUP BY` прямо в базе, без промежуточного использования pandas.

### 2. Обработка пропусков и очистка
- Заказы без ответа на опрос удовлетворённости (`review_score` пропущен, 646 строк) удалены, без метки нет смысла держать строку в обучающей выборке.
- `product_category` — пропуски (1 359 строк, разорванная связь с таблицей товаров) заполнены как `'unknown'`, а не удалены, чтобы не терять 1.4% данных.
- `product_photos_qty` — пропуски заполнены медианой.
- Обнаружены физически невозможные отрицательные значения `shipping_prep_days` и `carrier_to_customer_days` (дата передачи перевозчику раньше даты покупки) — такие строки удалены как ошибки в исходных данных.
- Целевая переменная содержала нецелые значения (`4.5`, `3.33` и т.п.) — артефакт агрегации нескольких отзывов на один заказ через `AVG()` в SQL, исправлено округлением до целого.

### 3. Разведочный анализ (EDA)
Ключевые находки (полные визуализации и выводы — в ноутбуке):
- ~79% заказов получают 4–5 звёзд, но оценка "1" (9.7%) встречается чаще, чем "2" и "3" по отдельности. Клиенты чаще ставят либо максимум, либо явный минимум, промежуточные оценки редки.
- Заказы, доставленные с опозданием относительно обещанного срока, устойчиво получают более низкие оценки. Во всех моделях это оказался главный фактор.
- Мебель, крупногабаритная техника и одежда получают более низкие оценки (сложности в перевозке, несоответствие ожиданиям); книги, канцелярия и мелкая техника — стабильно высокие.
- Клиенты с оценкой 1–2 в среднем платили за доставку больше.

### 4. Целевая переменная
Оценка 1–5 бинаризована: `target = 1`, если `review_score >= 4` (клиент доволен), иначе `0`. Баланс классов после бинаризации — 79% / 21%, поэтому во всех моделях использовано взвешивание классов (`class_weight='balanced'` / `auto_class_weights='Balanced'`).

### 5. Машинное обучение
Обучены и сопоставлены три модели: **Logistic Regression**, **Random Forest** и **CatBoost**. Числовые признаки масштабированы (`StandardScaler`), категориальные закодированы (`OneHotEncoder`), пропуски заполнены (`SimpleImputer`). Разбиение на train/test — 80/20 со стратификацией по таргету.

| Модель | ROC-AUC | Accuracy | Precision (риск) | Recall (риск) | F1 (риск) |
|---|---|---|---|---|---|
| Logistic Regression | 0.700 | 0.71 | 0.38 | 0.54 | 0.44 |
| Random Forest | 0.705 | 0.77 | 0.46 | 0.46 | 0.46 |
| CatBoost | 0.712 | 0.75 | 0.42 | 0.49 | 0.45 |

*«Риск» — класс 0 (недовольные клиенты), то есть именно та группа, которую бизнесу важно ловить.*

CatBoost лидирует по ROC-AUC, но Random Forest немного точнее по метрикам класса риска, а Logistic Regression лучше всего «вылавливает» недовольных клиентов (recall 0.54) ценой большего числа ложных срабатываний. Выбор итоговой модели зависит от того, что бизнесу важнее — не пропустить недовольного клиента (recall) или не тратить бюджет на компенсации довольным (precision).

### Важность признаков
Во всех трёх моделях главный предиктор — **`delivery_delay_days`** (опоздание относительно обещанного срока) и **`total_delivery_days`** (общее время доставки). Далее по значимости — время передачи перевозчику, вес товара и стоимость доставки.

## Бизнес-рекомендации

- Указывать клиенту дату доставки с запасом в 1 день, чтобы фактическая доставка "раньше срока" стабильно давала повод для высокой оценки.
- При прогнозируемом риске задержки проактивно предлагать компенсацию или бонус клиенту, предотвращая негативный отзыв ещё до его появления.
